# EDKAR CRM — полная передаточная документация

**Актуальность:** 26.07.2026  
**Версия установщика:** 1.0.0  
**Назначение документа:** самодостаточный контекст для продолжения разработки в новой задаче. Перед изменениями новый исполнитель должен прочитать документ целиком и сверить код с указанными путями.

## 1. Что это за система

`ClinicStatisticsApp` развивается из «Системы статистики» в единую CRM-платформу сети частной стоматологии и медицины EDKAR.

Система объединяет:

- управленческую статистику филиалов;
- колл-центр MANGO Office;
- внутренние задачи, календарь, почту и чат;
- CRM-карточки пациентов;
- сводную CRM-аналитику по записям, оплатам, удержанию и первичным пациентам.

Рабочие медицинские базы филиалов работают на Firebird/IBExpert и **не изменяются приложением**. Центральная SQL-база CRM хранит собственные проекции, связи, снимки, результаты импорта и пользовательские решения.

## 2. Главные правила и ограничения

### 2.1. Firebird только для чтения

Это ключевое правило проекта.

- Не выполнять `INSERT`, `UPDATE`, `DELETE`, DDL и любые «исправления» в Firebird.
- Не менять структуру рабочих баз филиалов.
- Все импорты Firebird — `SELECT` и чтение метаданных.
- Любое объединение пациентов, CRM-заметки, причины ухода, статусы и связи хранятся только в SQL CRM.

### 2.2. Один пациент в разных филиалах

В сети 11 независимых баз. Одинаковый человек может иметь разные локальные идентификаторы и одинаковый/разный номер карты в нескольких филиалах. Это не глобальный пациент до ручного или подтверждённого объединения.

Правильная модель:

```text
CRM-пациент (CrmPerson)
 ├─ карточка филиала ЦК       (ExternalPatientCard)
 ├─ карточка филиала Альфа    (ExternalPatientCard)
 ├─ карточка филиала Детство  (ExternalPatientCard)
 └─ ...
```

`SourcePatientId` действует только внутри конкретного источника Firebird. Его нельзя использовать как глобальный идентификатор.

### 2.3. Секреты

- Не записывать в Git и документацию ключи MANGO, пароли Firebird, SQL и почты.
- Локальные секреты MANGO: `ClinicStatisticsApp.UI\appsettings.Local.json`.
- Пример без ключей: `appsettings.Local.example.json`.
- Конфигурация Firebird — `ClinicStatisticsApp.UI\firebird.Local.json`; в установщик должна попадать только согласованная локальная конфигурация.

### 2.4. SQL и VPN

Центральная SQL-база: `ClinicStatisticsDb`, сервер обычно `SQL,1433`. При VPN первое подключение может быть долгим; для диагностики SQL использовать увеличенный таймаут подключения, не менее 55 секунд.

### 10.2. Импорт карт

Страница: `FirebirdSyncPage.xaml(.cs)`.

Сервис: `ExternalPatientSynchronizationService` и чтение Firebird в `Integrations\Firebird`.

Импортирует только данные, допустимые для CRM-проекции: локальный ID, номер карты, ФИО, дата рождения, телефоны, e-mail и служебные сведения. Медицинская информация не копируется в эту базовую проекцию.

Импорт может запускаться для одного выбранного источника или всех баз. Ошибки по источникам показываются в истории импорта; успешные источники не откатываются из-за ошибки другого.

### 10.3. Поиск и дубли

Страницы:

- `PatientDirectoryPage.xaml(.cs)` — единая клиентская база;
- `DuplicateReviewPage.xaml(.cs)` — проверка совпадений;
- `CrmProfileMergeWindow.xaml(.cs)` — ручное объединение CRM-профилей.

Правила:

- поиск поддерживает несколько слов, номер карты и часть ФИО;
- точная сильная пара для предложений: одинаковый номер карты + нормализованное ФИО в разных источниках;
- объединение всегда ручное и аудируемое;
- объединённые группы не должны снова появляться в очереди дублей;
- при объединении обычной карты с CRM-профилем целевым должен быть CRM-профиль;
- номер целевой CRM-карты сохраняется, он не должен заменяться номером присоединяемой карты;
- не совпадающее отчество допустимо для ручного объединения: исходные филиальные карты не удаляются и не меняются, меняется только связь с единым `CrmPerson`.

### 10.4. Как отображать объединённого пациента

В поиске единый CRM-пациент должен быть одной строкой. Карты филиалов — дочерние источники внутри карточки/правой панели. Не выводить одновременно множество строк со статусом «Единый CRM-пациент» для одной и той же объединённой сущности.

## 11. Досье пациента

Окно: `PatientDossierWindow.xaml(.cs)`. Детали приёма: `VisitDetailsWindow.xaml(.cs)`.

Открывается двойным кликом по карточке пациента.

Принципы:

- читает Firebird только по связанным картам;
- объединённая CRM-карта показывает сведения всех входящих филиалов;
- данные визуально разделены по вкладкам и блокам, а не одной технической строкой;
- технические имена полей заменяются на пользовательские русские названия;
- в записях и услугах отображается филиал и номер карты-источника;
- есть ручная кнопка «Обновить»;
- после чтения результат сохраняется в SQL-снимок;
- при повторном открытии показывается SQL-снимок без повторного чтения Firebird;
- при недоступном Firebird открывается последний сохранённый снимок с явным указанием времени снимка.

Вкладки досье:

- Обзор;
- Анкета и контакты;
- Приёмы и услуги;
- Работы;
- Записи.

Требование развития: для каждого конфликта между филиалами отображать название поля и конкретные значения по каждому филиалу.

## 12. CRM-аналитика

Страница:

```text
ClinicStatisticsApp.UI\Views\CrmAnalyticsPage.xaml(.cs)
```

Сервис и локальный склад:

```text
ClinicStatisticsApp\Services\CrmAnalyticsWarehouseService.cs
ClinicStatisticsApp\Integrations\Firebird\FirebirdAnalyticsReader.cs
```

### 12.1. Общая логика

1. Пользователь выбирает источник и диапазон дат.
2. Нажимает «Обновить данные из Firebird».
3. Приложение читает Firebird и заменяет **только строки выбранного источника за выбранный период** в SQL-складе.
4. Все сводки фильтруются одновременно по источнику **и выбранному периоду**. Нельзя считать их по всем ранее загруженным датам.
5. Во время импорта отображается статус; Firebird не изменяется.

По умолчанию для тестирования следует использовать только источник «Копия ЦК (тест)», чтобы не нагружать рабочие базы.

### 12.2. Источники Firebird для аналитики

| Firebird-таблица | Использование |
|---|---|
| `INDEXF_2` | оплаты: дата, сумма, пациент, описание, касса |
| `SETKA` | активные записи к врачу |
| `SETKA_LOG` | снятые записи, отсутствующие в текущей `SETKA` |
| `TYP_NAZ` | справочник типов записи |
| `PACIENT` | код причины ухода `PRICH_UHODA`, администратор карты `IDADM_CARD` |
| `SOTRUDNIKITEMP` | ФИО врача и администратора |

### 12.3. Типы записей

`SETKA.TYP_NAZ` хранит **числовой код**, не текст из интерфейса MedM:

| Код | Короткое имя MedM | Значение |
|---:|---|---|
| 80 | ПерК | первичный в клинике |
| 60 | ПерВ | первичный у врача |
| 62 | Снят | снятый приём |
| 59 | План | плановый приём |
| 23 | Конс | консультация |
| 63 | Осмо | осмотр |

ПерК и ПерВ должны рассчитываться по кодам `80` и `60`, а не сравнением с текстом.

### 12.4. Неявка, состоявшийся приём и снятая запись

- `NOTCOMING` — явный признак неявки.
- Пустой `NOTCOMING` **не является доказательством**, что пациент пришёл.
- Поэтому на воронке используется честная формулировка «не отмечены как неявка», а не «пришли».
- Снятые записи извлекаются отдельно из `SETKA_LOG` с `TYP_NAZ = 62` и отображаются отдельно от неявок.
- `IDPRIEM` найден в записях тестовой базы, но сам по себе не должен трактоваться как доказательство состоявшегося визита без отдельной проверки бизнес-логики MedM.

### 12.5. Вкладки аналитики

| Вкладка | Что показывает |
|---|---|
| Воронка | активные записи, не отмеченные как неявка, будущие записи, явные неявки, снятые, ПерК/ПерВ |
| Записи | активные записи, пациенты, неявки, снятые, врачи, кабинеты |
| Финансы | число оплат, оплаченная сумма, средний чек |
| Удержание | пациенты без записи более шести месяцев; очередь возврата — следующий этап |
| Первичные | ПерК/ПерВ, разбивка по врачам, список первичных пациентов |

### 12.6. Вкладка «Первичные пациенты и приход к врачам»

Реализована на базе уже загруженного аналитического склада. Переключение вкладки не должно заново обращаться к Firebird.

Возможности:

- общий счёт ПерК и ПерВ за выбранный период;
- таблица врачей: всего, 1 визит, 2 визита, 3 и более, среднее число визитов;
- таблица пациентов: ФИО, № карты, тип, врач, дата, число визитов, администратор, причина ухода;
- у обеих таблиц должны работать вертикальная и горизонтальная прокрутка;
- показатели ПерК/ПерВ совпадают с воронкой: пациент с обоими типами входит в оба счётчика, но в детализации показывается одной строкой.

Ограничение: поле причины ухода приходит кодом. В SQL CRM создана `CrmDepartureReasonMappings`.

- Код `0` предзаполнен как «Не определено».
- Неизвестные коды выводятся как `Код N (не расшифрован)`.
- Нельзя угадывать расшифровку или менять Firebird. Нужен отдельный интерфейс администрирования справочника, где пользователь один раз сопоставит код с «Дорого», «Не требуется», «Придут позже», «Другое» и т. п.

### 12.7. Что ещё нужно развить в аналитике

1. Детальная воронка стадий CRM с историей и временем на этапе.
2. Переход по каждой цифре в конкретный список пациентов/записей/звонков.
3. Конверсии «звонок → запись → визит → оплата».
4. Отдельная достоверная логика факта визита после проверки MedM.

## 14. База SQL и создание таблиц

Часть CRM-таблиц создаётся/дополняется сервисами через `EnsureStorageAsync`. Это допустимо только для SQL CRM.

При развитии:

- делать миграции идемпотентными (`IF OBJECT_ID`, `IF COL_LENGTH`, проверки индексов);
- не удалять исторические CRM-связи без аудита;
- не изменять Firebird ради удобства схемы;
- для крупных изменений добавить отдельный SQL-скрипт в `Database` и документировать порядок применения.
