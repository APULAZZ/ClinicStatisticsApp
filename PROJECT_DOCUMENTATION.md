## 1. Что это за система

`ClinicStatisticsApp` развивается из «Системы статистики» в единую CRM-платформу сети частной стоматологии и медицины EDKAR.

Система объединяет:

- управленческую статистику филиалов;
- колл-центр MANGO Office;
- внутренние задачи, календарь, почту и чат;
- CRM-карточки пациентов;
- сводную CRM-аналитику по записям, оплатам, удержанию и первичным пациентам.

Рабочие медицинские базы филиалов работают на Firebird/IBExpert и **не изменяются приложением**. Центральная SQL-база CRM хранит собственные проекции, связи, снимки, результаты импорта и пользовательские решения.

## 2. Главные правила и ограничения

### 2.1. Firebird только для чтения

Это ключевое правило проекта.

- Не выполнять `INSERT`, `UPDATE`, `DELETE`, DDL и любые «исправления» в Firebird.
- Не менять структуру рабочих баз филиалов.
- Все импорты Firebird — `SELECT` и чтение метаданных.
- Любое объединение пациентов, CRM-заметки, причины ухода, статусы и связи хранятся только в SQL CRM.

### 2.2. Один пациент в разных филиалах

В сети 11 независимых баз. Одинаковый человек может иметь разные локальные идентификаторы и одинаковый/разный номер карты в нескольких филиалах. Это не глобальный пациент до ручного или подтверждённого объединения.

Правильная модель:

```text
CRM-пациент (CrmPerson)
 ├─ карточка филиала ЦК       (ExternalPatientCard)
 ├─ карточка филиала Альфа    (ExternalPatientCard)
 ├─ карточка филиала Детство  (ExternalPatientCard)
 └─ ...
```

`SourcePatientId` действует только внутри конкретного источника Firebird. Его нельзя использовать как глобальный идентификатор.

### 2.3. Секреты

- Не записывать в Git и документацию ключи MANGO, пароли Firebird, SQL и почты.
- Локальные секреты MANGO: `ClinicStatisticsApp.UI\appsettings.Local.json`.
- Пример без ключей: `appsettings.Local.example.json`.
- Конфигурация Firebird — `ClinicStatisticsApp.UI\firebird.Local.json`; в установщик должна попадать только согласованная локальная конфигурация.

### 2.4. SQL и VPN

Центральная SQL-база: `ClinicStatisticsDb`, сервер обычно `SQL,1433`. При VPN первое подключение может быть долгим; для диагностики SQL использовать увеличенный таймаут подключения, не менее 55 секунд.

### Связь звонков с CRM

CRM связывает звонки по нормализованному номеру телефона. В карточке пациента показывается история привязанных коммуникаций. Нажатие на звонок должно открывать карточку звонка с доступной записью разговора; при отсутствии записи нужно явно показывать причину, а не создавать пустую карточку.

### Последние звонки в карточке пациента

- В правой панели «Единой клиентской базы», непосредственно в блоке **«Последние звонки из MANGO»**, есть кнопка **«Последние звонки»**. Не путать её с кнопкой **«Связать звонки Mango»**: последняя связывает с CRM уже импортированные записи колл-центра.
- Функция обращается только к MANGO API и только на чтение. Firebird, рабочие базы клиник и SQL CRM при самом поиске не изменяются.
- В поиск передаются номера текущей и всех дочерних карт объединённого CRM-пациента. Номера нормализуются: формат `8…`, `+7…`, пробелы, скобки и дефисы не мешают сравнению.
- MANGO API возвращает статистику за период, а не гарантированный результат по одному номеру. Поэтому приложение проверяет недельные интервалы от текущего момента назад, прекращая запрос сразу после нахождения **пяти** звонков либо после достижения глубины **30 дней**. Это быстрее и безопаснее, чем единый запрос за весь месяц.
- В таблице показываются до пяти последних звонков: **дата и время**, **направление** и **сотрудник**, с которым разговаривал пациент. Если сотрудника MANGO не определил, явно выводится «Не определён».
- Во время работы строка статуса показывает текущий проверяемый период и число найденных записей. Кнопка **«Остановить»** появляется только во время запроса; она отменяет сетевой запрос и не создаёт частичных связей или записей.
- Если за 30 дней найдено меньше пяти звонков, пользователю показывается фактическое число. Исторический поиск старше 30 дней — отдельная будущая функция, поскольку он может заметно нагрузить MANGO.

### 10.2. Импорт карт

Страница: `FirebirdSyncPage.xaml(.cs)`.

Сервис: `ExternalPatientSynchronizationService` и чтение Firebird в `Integrations\Firebird`.

Импортирует только данные, допустимые для CRM-проекции: локальный ID, номер карты, ФИО, дата рождения, телефоны, e-mail и служебные сведения. Медицинская информация не копируется в эту базовую проекцию.

Импорт может запускаться для одного выбранного источника или всех баз. Ошибки по источникам показываются в истории импорта; успешные источники не откатываются из-за ошибки другого.

### 10.3. Поиск и дубли

Страницы:

- `PatientDirectoryPage.xaml(.cs)` — единая клиентская база;
- `DuplicateReviewPage.xaml(.cs)` — проверка совпадений;
- `CrmProfileMergeWindow.xaml(.cs)` — ручное объединение CRM-профилей.

Правила:

- поиск поддерживает несколько слов, номер карты и часть ФИО;
- точная сильная пара для предложений: одинаковый номер карты + нормализованное ФИО в разных источниках;
- объединение всегда ручное и аудируемое;
- объединённые группы не должны снова появляться в очереди дублей;
- при объединении обычной карты с CRM-профилем целевым должен быть CRM-профиль;
- номер целевой CRM-карты сохраняется, он не должен заменяться номером присоединяемой карты;
- не совпадающее отчество допустимо для ручного объединения: исходные филиальные карты не удаляются и не меняются, меняется только связь с единым `CrmPerson`.

### 10.4. Как отображать объединённого пациента

В поиске единый CRM-пациент должен быть одной строкой. Карты филиалов — дочерние источники внутри карточки/правой панели. Не выводить одновременно множество строк со статусом «Единый CRM-пациент» для одной и той же объединённой сущности.

Правая панель `PatientDirectoryPage` содержит, помимо карт филиалов, задач и привязанных коммуникаций, отдельный live-блок «Последние звонки из MANGO». Он не является импортом и не должен автоматически создавать `CrmActivityLinks`: это быстрый просмотр актуальной телефонной истории пациента.

## 11. Досье пациента

Окно: `PatientDossierWindow.xaml(.cs)`. Детали приёма: `VisitDetailsWindow.xaml(.cs)`.

Открывается двойным кликом по карточке пациента.

Принципы:

- читает Firebird только по связанным картам;
- объединённая CRM-карта показывает сведения всех входящих филиалов;
- данные визуально разделены по вкладкам и блокам, а не одной технической строкой;
- технические имена полей заменяются на пользовательские русские названия;
- в записях и услугах отображается филиал и номер карты-источника;
- есть ручная кнопка «Обновить»;
- после чтения результат сохраняется в SQL-снимок;
- при повторном открытии показывается SQL-снимок без повторного чтения Firebird;
- при недоступном Firebird открывается последний сохранённый снимок с явным указанием времени снимка.

Вкладки досье:

- Обзор;
- Анкета и контакты;
- Приёмы и услуги;
- Работы;
- Записи.

Требование развития: для каждого конфликта между филиалами отображать название поля и конкретные значения по каждому филиалу.

## 12. CRM-аналитика

Страница:

```text
ClinicStatisticsApp.UI\Views\CrmAnalyticsPage.xaml(.cs)
```

Сервис и локальный склад:

```text
ClinicStatisticsApp\Services\CrmAnalyticsWarehouseService.cs
ClinicStatisticsApp\Integrations\Firebird\FirebirdAnalyticsReader.cs
```

### 12.1. Общая логика

1. Пользователь выбирает источник и диапазон дат.
2. Нажимает «Обновить данные из Firebird».
3. Приложение читает Firebird и заменяет **только строки выбранного источника за выбранный период** в SQL-складе.
4. Все сводки фильтруются одновременно по источнику **и выбранному периоду**. Нельзя считать их по всем ранее загруженным датам.
5. Во время импорта отображается статус; Firebird не изменяется.

По умолчанию для тестирования следует использовать только источник «Копия ЦК (тест)», чтобы не нагружать рабочие базы.

### 12.2. Источники Firebird для аналитики

| Firebird-таблица | Использование |
|---|---|
| `INDEXF_2` | оплаты: дата, сумма, пациент, описание, касса |
| `SETKA` | активные записи к врачу |
| `SETKA_LOG` | снятые записи, отсутствующие в текущей `SETKA` |
| `TYP_NAZ` | справочник типов записи |
| `PACIENT` | код причины ухода `PRICH_UHODA`, администратор карты `IDADM_CARD` |
| `SOTRUDNIKITEMP` | ФИО врача и администратора |

### 12.3. Типы записей

`SETKA.TYP_NAZ` хранит **числовой код**, не текст из интерфейса MedM:

| Код | Короткое имя MedM | Значение |
|---:|---|---|
| 80 | ПерК | первичный в клинике |
| 60 | ПерВ | первичный у врача |
| 62 | Снят | снятый приём |
| 59 | План | плановый приём |
| 23 | Конс | консультация |
| 63 | Осмо | осмотр |

ПерК и ПерВ должны рассчитываться по кодам `80` и `60`, а не сравнением с текстом.

### 12.4. Неявка, состоявшийся приём и снятая запись

- `NOTCOMING` — явный признак неявки.
- Пустой `NOTCOMING` **не является доказательством**, что пациент пришёл.
- Поэтому на воронке используется честная формулировка «не отмечены как неявка», а не «пришли».
- Снятые записи извлекаются отдельно из `SETKA_LOG` с `TYP_NAZ = 62` и отображаются отдельно от неявок.
- `IDPRIEM` найден в записях тестовой базы, но сам по себе не должен трактоваться как доказательство состоявшегося визита без отдельной проверки бизнес-логики MedM.

### 12.5. Вкладки аналитики

| Вкладка | Что показывает |
|---|---|
| Воронка | активные записи, не отмеченные как неявка, будущие записи, явные неявки, снятые, ПерК/ПерВ |
| Записи | активные записи, пациенты, неявки, снятые, врачи, кабинеты |

### 12.6. Вкладка «Первичные пациенты и приход к врачам»

Реализована на базе уже загруженного аналитического склада. Переключение вкладки не должно заново обращаться к Firebird.

Возможности:

- общий счёт ПерК и ПерВ за выбранный период;
- таблица врачей: всего, 1 визит, 2 визита, 3 и более, среднее число визитов;
- таблица пациентов: ФИО, № карты, тип, врач, дата, число визитов, администратор, причина ухода;
- у обеих таблиц должны работать вертикальная и горизонтальная прокрутка;
- показатели ПерК/ПерВ совпадают с воронкой: пациент с обоими типами входит в оба счётчика, но в детализации показывается одной строкой.

Ограничение: поле причины ухода приходит кодом. В SQL CRM создана `CrmDepartureReasonMappings`.

## 19. Воронка имплантов

### 19.1. Назначение и статус

Раздел **«Воронка имплантов»** находится в меню CRM. Он автоматизирует путь лида с лендинга имплантов:

```text
выгрузка заявок и звонков → Mango-теги → запись MedM → явка → оплаты пациента
```

Цель — заменить ручное сведение файлов №1–№4 воспроизводимым отчётом, сохраняя возможность проверить каждое автоматическое сопоставление. Firebird используется только для чтения; все импортированные данные, связи и результаты живут в `ClinicStatisticsDb`.

Основные файлы реализации:

| Файл | Назначение |

| `ClinicStatisticsApp.UI\Views\ImplantFunnelPage.xaml.cs` | кнопки, чтение Excel, период и прогресс |
| `ClinicStatisticsApp\Services\ImplantFunnelService.cs` | импорт лидов, Mango-сопоставление, расчёт отчёта, проверочная таблица |
| `ClinicStatisticsApp\Services\CrmAnalyticsWarehouseService.cs` | импорт расписания и оплат из Firebird в SQL CRM |
| `ClinicStatisticsApp\Integrations\Firebird\FirebirdImplantEventReader.cs` | read-only чтение журнала MedM (`LOG_EVENTS`) |
| `ClinicStatisticsApp\Integrations\Firebird\FirebirdAnalyticsReader.cs` | read-only чтение расписания и оплат |

### 19.2. Источники и их смысл

| Источник | Содержимое | Роль в воронке |
|---|---|---|
| Файл №1, Excel | листы заявок и звонков лендинга | начальная база лидов |
| Mango Office | факт разговора, направление, участник и тема/тег | подтверждение «запись / не запись / сброс» |
| MedM `LOG_EVENTS` | события «Назначен» (тип 12) и «Пришёл» (тип 22) | подтверждение записи и явки |
| Firebird `SETKA`, `SETKA_LOG`, `INDEXF_2` | расписание, отмены, оплаты | дата приёма, статус, выручка |
| SQL CRM | копии и результаты обработки | единственное место, куда приложение пишет |
| Файлы №2 и №3 | ручная проверка операторов и филиалов | эталон для сверки и разбор спорных лидов |
| Файл №4 | итог по филиалам за месяц | контрольный итог и бюджет периода |

В файле №4 вручную вводится **только бюджет**. Записи, явки, суммы и производные показатели должны рассчитываться автоматически, но до окончания сверки исторических периодов файл №4 остаётся контрольным источником.

### 19.3. Поддерживаемые форматы файла №1

Импорт понимает оба известных варианта:

- старый шаблон: листы `Заявки` и `Звонки`;
- январский шаблон 2026: листы `Заявки Импланты` и `Звонки Импланты`.

Для заявок заголовки находятся по названиям `Phone` и `Date`; для звонков возможны несколько блоков заголовков в одном листе. Из файла берутся только строки, чья дата попадает в выбранный на странице период. Поэтому нельзя случайно смешать январский отчёт с данными другого месяца из широкого файла.

Телефоны нормализуются до цифрового вида с кодом `+7`; пробелы, скобки, дефисы, `=`, апострофы и прочие символы не влияют на сравнение. Такая же нормализация применяется к телефонам из скопированных карточек Firebird.

### 19.4. Порядок работы пользователя

Для нового периода:

1. Выбрать даты начала и конца периода. Период определяет состав лидов и месяц их привлечения.
2. Нажать **«Загрузить файл заявок и звонков»** и выбрать файл №1. Статус показывает имя файла, число найденных строк и число новых лидов.
3. При необходимости нажать **«Обновить Mango: звонки и теги»**. Mango запрашивается по дням; в журнале есть разделители дат и отображается, сколько звонков получено, сколько совпало с файлом №1 и сколько тегов распознано.
4. Нажать **«Обновить карточки и телефоны»**, если телефонный индекс ещё не обновлялся или появились новые карточки. Эта операция копирует карточки и телефоны всех рабочих филиалов в SQL CRM. Firebird не меняется.
5. Нажать **«Обновить MedM, записи и оплаты»**. Для лидов выбранного месяца операция дочитывает результаты от даты лида до сегодняшней даты: записи, явки и оплаты. Это нужно, потому что январский лид может прийти в феврале, а оплатить лечение позднее.
6. Нажать **«Показать отчёт»**. Эта кнопка строит отчёт только из уже сохранённых данных SQL CRM и не обращается к Mango или Firebird.
7. При необходимости ввести бюджет и нажать **«Сохранить»**. Бюджет хранится для точного диапазона дат.

Кнопка **«Сравнить периоды»** строит сравнение по месяцам либо годам внутри выбранного диапазона; она также не запускает внешние запросы.

### 19.5. Mango: классификация тем

Темы Mango поставляются раздельно для входящих и исходящих вызовов. Правила каталога `CallCenterTopicCatalog`:

| Группа тем | Классификация в воронке |
|---|---|
| `Вх ПЛАН`, `Вх ПЕРК`, `Исх ПЛАН`, `Исх ПЕРК` и их темы по филиалам | `Запись` |
| `Вх Не запись`, `Исх Не запись` и дочерние темы | `Не запись` |
| `Вх Сброс`, `Исх Сброс` | `Сброс` |
| отсутствующая или нераспознанная тема | `Без классификации` |

Для строки с листа «Звонки» ожидается входящий вызов; для строки «Заявки» — исходящий обратный звонок. Mango возвращает дневной список звонков, но в CRM сохраняются и классифицируются только записи, совпавшие с телефоном, временем (допуск ±3 часа с учётом московского времени выгрузки) и направлением из файла №1.

Mango — отдельное подтверждение результата разговора. Он не заменяет MedM: число тегов «Запись» и число подтверждённых записей MedM могут различаться.

### 19.7. Правило длинного приёма в расписании

Сетка MedM состоит из коротких временных слотов. Несколько последовательных слотов одного пациента у одного врача в один день — это **один длительный приём**, а не несколько записей.

При импорте `FirebirdAnalyticsReader` читает `SETKA.DATEPR` и `SETKA.TIMEPR`. Последовательные слоты того же пациента, врача и дня с интервалом не более 30 минут объединяются в одну запись CRM; сохраняется первый слот блока. Отдельные дни, другие врачи и разрывы более 30 минут остаются самостоятельными приёмами. Отменённые записи (`SETKA_LOG`) не объединяются с активными.

После изменения этого правила уже загруженный период необходимо обновить кнопкой **«Обновить MedM, записи и оплаты»**, чтобы SQL CRM пересобрала свой снимок расписания.

### 19.8. Оплаты и атрибуция выручки

Выручка отчёта — сумма оплат сопоставленного пациента после найденного приёма. Она относится к месяцу лида, а не к месяцу кассовой операции. Это соответствует смыслу файла №4: пациент может прийти позднее месяца обращения и продолжить лечение/оплату позднее.

До появления специализированной метки «импланты» сумма включает все услуги сопоставленного пациента после записи. Это ограничение должно быть видно в интерфейсе и не должно скрываться: показатель отражает атрибутированную выручку, а не гарантированно только имплантационные услуги.

### 19.9. Что хранится в SQL CRM

Таблицы создаются через `ImplantFunnelService.EnsureStorageAsync`; это допустимо только для SQL CRM:

| Таблица | Содержимое |
|---|---|
| `ImplantFunnelLeads` | строки файла №1, нормализованный телефон, Mango-результат |
| `ImplantFunnelMedmEvents` | скопированные события MedM типов 12 и 22 |
| `ImplantFunnelOperatorMappings` | связь операторов колл-центра и пользователей MedM |
| `ImplantFunnelBudgets` | вручную введённые бюджеты периодов |
| `CrmPatientContactPhones` | CRM-индекс телефонов карточек пациентов |
| `CrmAnalyticsAppointments` | снимок расписания и статусов, без дублей длительных приёмов |
| `CrmAnalyticsPayments` | снимок оплат из Firebird |

Не удалять эти таблицы или исторические данные при доработке отчёта без отдельного согласованного плана миграции.

### 19.10. Экран отчёта и пояснения показателей

- Цветные карточки: лиды, записи Mango, подтверждения MedM, подтверждённые явки, оплаты, стоимость лида, стоимость явки, выручка/бюджет.
- Конверсионная воронка: проценты для MedM считаются от лидов, для явок — от MedM-записей. Оплаты отображаются суммой, а не фиктивным процентом.
- Динамика: синим показаны лиды, зелёным — записи по Mango. Точные значения и доля Mango от лидов показаны во всплывающей подсказке.
- По филиалам всегда выводятся все рабочие базы, включая нулевые, плюс строка «Всего».
- Сравнение периодов показывает маленькие воронки по периодам и таблицу с изменением лидов, MedM, явок и выручки.
- Внизу находится таблица **«Проверка сопоставления лидов»**: дата, телефон, оператор, найденный филиал, номер карты, дата приёма и статус. Строки «Не найдена запись» — рабочая очередь для точечной сверки с файлами №2/№3 и Mango.

### 19.11. Контрольная сверка: январь 2026

## 20. Воронка посещений

### 20.1. Назначение

Раздел CRM **«Воронка посещений»** заменяет ручной файл `Воронка посещений.xlsx`. Он строит помесячную статистику рабочих филиалов по данным MedM:

- уникальные пациенты;
- посещения;
- коэффициент посещений: `посещения / пациенты`.

Раздел доступен из левого меню CRM. Начальная страница — **«Обзор по клиникам»**.

### 20.2. Точное правило MedM «В услугах»

Контрольная сверка показала, что всплывающее окно MedM при включённом переключателе **«В услугах»** считает не строки `INDEXF` и не отдельные услуги.

Правило расчёта:

```text
Пациенты   = число уникальных WORKPACIENT.NUM_PACIENT за период, исключая 0.
Посещения  = число уникальных пар (WORKPACIENT.NUM_PACIENT, WORKPACIENT.DATEWORK).
Коэффициент = посещения / пациенты.
```

То есть несколько работ одного пациента в один календарный день образуют **одно посещение**.

Контрольный эталон:

| Филиал | Период | Пациенты MedM | Посещения MedM |
|---|---|---:|---:|
| Центральная / ЦК | Январь 2026 | 964 | 1 419 |

После реализации правило даёт те же 964 пациента и 1 419 посещений.

### 20.3. Firebird и хранение SQL CRM

Firebird остаётся строго read-only. Чтение выполняет:

```text
ClinicStatisticsApp\Integrations\Firebird\FirebirdVisitFunnelReader.cs
```

Запрос читает сгруппированные `NUM_PACIENT`, `DATEWORK` из `WORKPACIENT`. Поле `ID_WORK` в ряде старых баз имеет дробный текстовый формат, поэтому не применяется как идентификатор. Для SQL-снимка формируется детерминированный технический ключ из пациента и даты работы.

В SQL CRM хранится таблица:

| Таблица | Назначение |
|---|---|
| `CrmVisitFunnelEntries` | снимок одного посещения пациента за календарный день по каждому источнику |

Таблица создаётся идемпотентно через `VisitFunnelService.EnsureStorageAsync`. При обновлении заменяются только записи выбранного источника за выбранный период.

### 20.4. Рабочие и тестовые источники

Кнопка **«Обновить рабочие базы»** импортирует только источники, у которых `ClinicDataSources.IsTest = 0`, и исключает тестовые базы. На первом этапе проверка выполнялась на «Копии ЦК (тест)»; после успешной сверки включены рабочие филиалы.

Наименование в интерфейсе нормализуется:

| Наименование источника | Отображение в отчёте |
|---|---|
| содержит «Москов» | `Детство (Моск)` |
| содержит «Сельма» | `Детство (Сельма)` |

### 20.5. Экран отчёта

Основная вкладка **«Обзор по клиникам»** повторяет принцип исходного Excel:

- клиники расположены строками;
- для каждого месяца одновременно показаны три столбца: `П` (пациенты), `Пос` (посещения), `К` (коэффициент);
- есть итоги за год по всем трём метрикам;
- год выбирается отдельным фильтром;
- цвет ячейки сравнивает её с аналогичным месяцем предыдущего года: зелёный — выше, красный — ниже, нейтральный — без изменения;
- подсказка ячейки показывает значение предыдущего года и разницу;
- пустые будущие месяцы показаны как `—`, а не как нулевые значения.

График для выбранной клиники либо всех клиник строит одновременно:

- синий — пациенты;
- зелёный — посещения;
- оранжевый — коэффициент по правой шкале.

Точки графика имеют подсказки со значением метрики. Отсутствующие месяцы разрывают линию, а не создают ложное падение к нулю.

Вкладка **«Подробно по месяцам»** оставляет построчный вид «клиника + месяц» для аудита данных.

### 20.6. Дополнительные вкладки и текущий статус

На странице также созданы вкладки:

| Вкладка | Текущий источник | Статус |
|---|---|---|
| `Рабочие итоги по специалистам` | SQL-снимок `CrmAnalyticsAppointments` | Нужна предметная сверка состава показателей с MedM |
| `Снялись с приёма` | отменённые записи `SETKA_LOG` без последующей активной записи пациента | Нужна сверка правила с пользователем |
| `Проверка карт` | SQL-снимок записей | Нужна конкретизация необходимых колонок и MedM-признаков |

Для вторичных вкладок используется `FirebirdAnalyticsReader`. В разных Firebird-базах признаки неявки и причины ухода могут быть записаны дробными строками. Импорт не должен завершаться ошибкой: дробный признак неявки интерпретируется как ненулевой, а невалидная причина ухода сохраняется как `null`.

Вкладки с деталями загружаются лениво: построение основного отчёта не читает и не привязывает к интерфейсу данные специалистов, отмен и проверки карт. Это исключает зависание окна после нажатия «Показать отчёт». Для «Проверки карт» при широком периоде выводятся последние 2 500 записей; строка состояния показывает полный объём и предлагает сузить период для полного списка.

## 21. Расписание врачей

### 21.1. Назначение и границы данных

Экран **«Расписание → Сетка врачей»** показывает расписание из SQL-снимка CRM. Firebird используется только при явном нажатии **«Обновить из Firebird»** и только для чтения. Изменения, сделанные на экране, сохраняются исключительно в центральной SQL CRM.

Источник расписания в Firebird — `SETKA` и связанные служебные данные. В SQL CRM сохраняются записи `CrmAnalyticsAppointments`. Импорт расписания не импортирует оплаты.

### 21.2. Режимы просмотра

- **День** — сетка ресурсов (врач + филиал) на выбранную дату.
- **Неделя** — один врач, дни недели в колонках. Для единого профиля в сетке видны записи всех связанных филиалов.
- **Период** — один врач и произвольный диапазон «с / по», не более 31 дня.

Для периода длиннее недели автоматически применяется компактный список по датам: время, филиал, пациент и статус. Он заменяет слишком узкую сетку из большого количества колонок.

В карточке записи отображаются время, пациент и филиал. Цвета: обычный приём, резерв, неявка и служебный блок. Фильтры статусов работают без нового запроса к Firebird.

### 21.3. Особые записи MedM

- `ID_PAC = 10` — техническое свободное окно; оно не выводится как пациент.
- `ID_PAC = 350000`, а также запись с признаком «резерв» — показывается как **РЕЗЕРВ**.
- Длительность карточки не должна перекрывать следующую запись: для плотной сетки высота ограничивается расстоянием до следующего слота.
- Если в старом SQL-снимке отсутствует ФИО пациента, экран однократно дочитывает выбранный период из Firebird и обновляет только снимок расписания.

### 21.4. Профили врачей между филиалами

Профиль решает задачу врача, который работает в нескольких независимых базах, где ФИО может отличаться. Связь создаётся на странице расписания:

1. Отметить нужные источники/филиалы и обновить из Firebird даты, на которых врач есть в каждом филиале.
2. Выбрать врача.
3. Нажать **«Связать филиалы»**.
4. Отметить соответствующие локальные записи врача и сохранить.

SQL CRM хранит профиль и пары `источник + локальный ID врача` в `CrmScheduleDoctorProfiles` и `CrmScheduleDoctorProfileLinks`. При выборе имени профиля фильтр использует эти локальные ID, а не только совпадение ФИО. Firebird не изменяется.

### 21.5. Служебные блоки и избранное

- **Служебный блок** (обед, планёрка, отпуск, служебное) создаётся для выбранного ресурса в `CrmScheduleBlocks`; доступно редактирование левой кнопкой и удаление правой кнопкой. Можно повторить блок по будням на восемь недель.
- **Избранное** сохраняется отдельно для каждого пользователя в `CrmScheduleFavoriteDoctors`. Кнопка «★ В избранное» добавляет или удаляет выбранного врача; избранные выводятся первыми.
- Кнопка **«Профили врачей»** показывает сохранённые профили и позволяет удалить ошибочную связь целиком. Для изменения состава профиля используется «Связать филиалы» и повторное сохранение.
- Обычная карточка записи открывается по щелчку и показывает данные только для просмотра: дату/время, филиал, врача, статус, кабинет и комментарий.
- Из карточки доступна кнопка **«Открыть пациента в CRM»**: открывается список пациентов CRM с уже введённым ФИО. Если карт несколько, пользователь выбирает нужную; автоматическое объединение не выполняется.
- **«Контроль данных»** показывает количество записей без ФИО или локального ID врача, потенциальные пересечения по одному ресурсу и число созданных профилей. Проверка не изменяет данные.

Над сеткой есть массовые действия **«Выбрать все»** и **«Снять все»** для источников. При вертикальной прокрутке сетки строка с именами врачей и филиалами остаётся закреплённой.
